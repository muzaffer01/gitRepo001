Diagram 2 of 3

Technical flow

Three test layers drive the same app and report into one gate. Everything past that gate forks into two publish paths — except the one deliberate failure demo, which skips the gate on purpose and lands directly in docs.

Vitest + RTL
Unit/component layer — imports app modules directly and renders them in jsdom, no real browser involved.
Playwright
End-to-end layer — installs and drives a real Chromium browser against the running dev server.
Cucumber
BDD layer — runs Given/When/Then .feature scenarios, but reuses the Chromium binary Playwright already installed rather than downloading its own. A real dependency, not just build ordering.
verify-app gate
The single point all three suites plus the production build and a manual browser pass report into — the signal everything downstream (GitHub, docs) trusts.
GitHub path
git commit, then gh auth login's device flow — the human has to personally click the final "Authorize" button, since GitHub's bot-detection rejects a scripted one — then git push.
Docs path
Each of the 8 doc types is written to docs/*.md first, then mirrored to Google Drive as a native Google Doc by trashing the stale file and recreating it — there's no in-place "replace content" call.
demo-failing-test
Runs one real, non-staged failing scenario in an isolated Vite config so it can't touch the gate, then still lands a defect report in the same docs path as everything else.
  • Decided: all three test layers must pass, plus the production build and a manual browser click-through, before verify-app reports green — no suite is optional.
  • Decided: Cucumber deliberately reuses Playwright's Chromium install rather than managing its own — see Fig. 3 for why that makes it a dependency, not a peer.
  • Decided: the local docs/*.md file is always written first or alongside the Drive mirror, never Drive-only, so the two can't silently diverge.

Diagram 3 of 3

Framework — dependency stack

What each layer needs under it to run at all. The one non-obvious coupling in this stack — Cucumber leaning on Playwright's already-installed browser instead of bringing its own — sits right where it happens, in the test layer.

App layer
The actual product under test — no backend, so this layer is entirely client-side state and mock data.
Test layer
Three independent suites, except Cucumber, which is not independent: it calls into the same Playwright/Chromium install rather than managing its own browser binary.
Publish layer
Two destinations kept in sync by process, not by any shared tooling — GitHub through the gh CLI's device flow, Google Drive through trash-then-recreate, because neither API offers what the other need supports directly.
  • Decided: Cucumber's browser dependency on Playwright is treated as a real coupling, not incidental ordering — removing or reordering the Playwright skill would break the BDD suite.
  • Decided: this stack runs entirely on the local machine's toolchain — there is no CI runner or remote build service in the loop.
